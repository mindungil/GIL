### Finding

**Tool events render AFTER assistant text in chat surface transcripts.**

Inspected `/tmp/gil-eval-loop/iter/1/L1/gil.log` and
`/tmp/gil-eval-loop/iter/1/L4/gil.log`: the agent's success-claim text
appears BEFORE the `[system] ⚒` lines for the tool calls that
produced the result. Architecturally, the chat REPL has two channels
(`chunkCh` for text, `eventCh` for tool events) and only drains
`eventCh` between turns via `drainEvents()` at the top of the outer
input loop (`cli/internal/chat/repl/loop.go:103`). The streaming-loop
that consumes text chunks (`loop.go:146-169`) doesn't touch event
channel at all.

This validates P31's design diagnosis (inline tool narration is the
real chat-surface gap) at the *implementation* level — the wiring
exists but is sequenced wrong.

### Hypothesis

Drain pending events at the top of every text-stream iteration. Since
`NextEvent` is non-blocking (`grpc_client.go:330`), this is cheap.
Plus a final drain after `chunkDone` closes catches events that
arrived between the last text chunk and the stream end.

### Fix shape

`cli/internal/chat/repl/loop.go`: introduce `drainPendingEvents`
closure inside the streaming block. Call it before each
`NextAssistantChunk` and once at end. Track `lastEndedWithNewline` so
`[system]` notes that fire mid-line get a leading `\n` to avoid
gluing onto previous text.

Regression test: `TestLoop_ToolEventsInterleaveWithAssistantText`
(`loop_test.go`) — given pending events + chunks, asserts SystemNote
appears in renderer call sequence BEFORE first AssistantText.

Commit: `af86f0d`.

### Post-fix bench delta (iter 2 verify-only)

L1's `tool_calls` count went UP (16→22) which seems wrong. Looking at
the post-fix log: the count rose because the renderer now emits TWO
distinct `[system] ⚒` lines per tool (one for call, one for ✓
result), where pre-fix some collapsed. This is rendering granularity
not actual tool call count — the daemon emitted the same number of
tool_call/tool_result Parts in both runs. **Need a smarter metric for
future iters** (count distinct `tool_call` Parts on the daemon side,
not on the rendered transcript).

Visual inspection of `iter/2/L1/gil.log`: first tool call now appears
BETWEEN the intro text and the mid-turn text — confirmed inline. But
the trailing burst (plan_steps result + edit_file + 2 verifies) still
appears AFTER the final summary text. Root cause: the LAST text chunk
rendered before chunkDone closed, and the event burst arrived between
those two — picked up by the final drain *after* the text already
printed. A truly correct fix requires merging both channels into one
wire-order-preserving stream (matches P31's full architectural
pointer for the chat narration redo). Not done in this iter — would
be a multi-task subagent dispatch.

**Carrying-over followup:** unify chunkCh/eventCh into a single typed
Part channel so wire-order is preserved end-to-end. Probably ~200 LOC
in `grpc_client.go` + one renderer interface tweak. Track as a P-numbered
plan if surfaced again in a later iter.
